## Verification and compatibility boundary

Local Windows checks: all `vllm_ascend` and `tests/ut` Python files compile;
`git diff --check` passes; focused Ruff checks pass after import formatting.
The rebase also adds regression cases for physical packed-page metadata,
duplicate pointers, invalid block counts, noncontiguous buffers and alignment.

Windows has no PyTorch/NPU runtime. A full test suite and hardware smoke are
not claimed by this source rebase. The NPU build/deployment task must record its
final SHA, native-library load checks, operator tests, end-to-end response and
accuracy results before the image is described as validated.

The branch name preserves the requested 0.30.0 deployment target; it does not
guarantee that an arbitrary unpatched vLLM 0.30.0 wheel has every API required by
new upstream main. In particular, validate `prepare_kernel_block_sizes`, flat
kernel-size lists, node-local Engram groups, the current V4.1 package layout,
and native Engram config against the deployed editable vLLM tree. Preserve
`VLLM_USE_V2_MODEL_RUNNER=0` for the requested MRV1 deployment.

AscendC/schema changes require a full vllm-ascend rebuild, not Python-only
installation. Reuse neither the old handoff `.so` files nor an image tag as
proof of provenance: record source HEAD and hashes of the newly loaded native
libraries in the resulting image.

## Incremental operator-schema build failure and fix

The first rebased build on POD.191 failed six `KvQuantSparseFlashAttention`
variants: OPC saw three requested outputs but the op store exposed one.
The source OpDef and newly generated INI both already declared three outputs.
However, the autogen and custom ops-info JSON files still contained the old
31-operator set and no `KvQuantSparseFlashAttention` entry. Their modification
time was approximately 885 seconds older than the regenerated INI. OPC then
resolved the toolkit's same-named built-in operator, which exposes only
`attention_out`.

The CMake rule generated JSON with an `OUTPUT` custom command but supplied
only order dependencies on opbuild targets. Changes to their undeclared INI
side effects therefore did not invalidate an existing JSON. The fix refreshes
this lightweight metadata in a custom target after opbuild, tracking both
the autogen JSON and custom copy as byproducts. The neighboring compile-command
generation already follows the same per-build pattern. No kernel ABI is
changed and no CANN installation is edited.

`tests/ut/_tools/test_ops_info_generation.py` exercises the actual CMake
function and INI parser with CMake/Ninja in temporary directories. Both
built-in and custom modes pass initial generation, a one-to-three-output
incremental schema change, and recovery of a deleted custom JSON copy. The
test passed on POD.191; substituting the unpatched CMake function reproduced
`1 != 3` failures in both modes. Existing live build directories were not
changed by this regression test.

Additional checks completed on CPU in the deployment container: eight
AST-isolated tests of the actual packed-page zeroer metadata and twelve tests
of actual Engram fixed-slot functions passed. These do not replace NPU kernel,
collective, or end-to-end validation.

The upstream verified vLLM pin is confirmed as
`ced6857afa0ea7b2e3f0846a62e1394e90f15607`, matching the local deployment
reference tree. Its flat kernel-size and node-local Engram APIs were checked.

The next incremental build exposed a second, independent generator defect:
`write_json_file` opened an existing file with `O_WRONLY | O_CREAT` and wrapped
that descriptor in `fdopen(..., "w")`, which does not truncate it. The new
valid JSON occupied 103379 characters while the physical file retained
213086 characters, leaving 109707 characters of old trailing content. Both
autogen and custom copies failed `json.load` with `Extra data`; the correct
three-output KvQuant and fourteen-input QLI schemas were present at the start
but unreadable as complete JSON. Adding `O_TRUNC` fixes shrinking schemas.
The regression now also covers the three-to-one-output transition before
testing deleted-copy recovery. A clean build would hide both incremental
defects, so validation deliberately reuses existing generated files.

Both modes reproduced `JSONDecodeError: Extra data` with the old parser and
passed with the truncation fix. For the final deployment build, preserve the
old `csrc/build` and `csrc/build_cache` as renamed diagnostic snapshots and
build from fresh directories. Earlier successful cached actions may have
resolved a different schema while custom metadata was invalid; they are not
acceptable provenance for the release image.

The current kernel-cache prepared inputs cover generated operator sources,
dependencies, shared headers and compiler-version metadata, but do not hash
the custom ops-info JSON or loaded optiling library contents. The recipe hashes
the `ASCEND_CUSTOM_OPP_PATH` string, not the content behind that path. Thus an
independently changed schema/tiling library at the same path is a cache
invalidation risk. Adding those semantic inputs needs a separate cache-focused
change and tests; this build must not reuse the affected old cache.
